# 性能与缓存审查（2026-10-19）

审查对象为当前工作区，包括尚未提交的改动；未修改业务代码。覆盖 React/store 更新、会话历史、右侧文件/Git、编辑器、连接与轮询、搜索/设置及 HTTP/WebSocket 服务。generated 为协议类型，不作为运行时优化重点。两位 GPT-6.1 Sol 子代理分别审查渲染和工作区链路，主代理复核会话缓存、时序和外围请求。

这是代码审查，不是全场景性能压测。kimi-webbridge 已连接现有 5180 工作台并读取真实页面，确认双环境在线、当前会话运行中、项目面板打开；后续 evaluate/切换调用超时，未取得可靠的请求计数或 React Profiler 数据。不能把桥接耗时认定为页面卡顿，也不能声称已动态复现所有发现。

## 结论

应该缓存，但当前不是完全没有缓存。核心问题是缓存有效性与展示资格混在一起、文件树缓存跟随组件销毁、刷新来源重复，以及每条增量消息触发过大的计算范围。

优先改善“返回立即可读、保持阅读位置、后台更新不闪屏”，然后减少后台读取和长历史重算。不要把所有会话 DOM 常驻作为缓存方案。

## 高优先级发现

### 1. 有正文仍可能在切回时重新进入加载态

证据：`src/features/sessions/store.ts:553` 的 hydrate 删除 historySynced，供新建、激活、分叉路径使用；`:731` 的立即展示分支却要求 historySynced.has(id)。未命中后 `:771` 设置 openingId，`:778` 非增量读取历史。`src/features/conversation/Timeline.tsx:966` 的 loading 分支替换正文。

这解释了为何不是每个会话都重现：已经成功读取过历史、未被重新 hydrate 的会话有缓存直出路径；新建/激活/分叉后，以及重连清空标记后的部分会话会重新加载。`syncReverted()` 也清标记，成功读回后没有 recordHistory。

建议拆分 hasRenderableContent、historyCompleteness、stale、refreshing。已有有效内容立即呈现，后台校验；真正未加载过的会话才显示骨架。回滚必须先截断失效内容，再加载真实历史，不能为了不闪屏展示已撤销内容。

### 2. 流式消息和计时器重新计算整段历史

证据：`sessions/store.ts:388` 通知直接 update；`shell/App.tsx:155` 全量订阅 sessions；`conversation/Timeline.tsx:988` 全量遍历 turn；TurnContent、Item、Markdown 没有稳定的 memo 边界。`conversation/Markdown.tsx:118` 每次执行解析和高亮。Timeline `:748` 运行中每秒更新时间，也触发整树计算；折叠过程 `:635` 使用 hidden，仍构造和渲染子节点。

用户影响：长会话越聊越重；阅读旧消息、滚动和继续输入会与当前输出争用主线程。

建议历史 turn/message 稳定引用和 memo；计时器下沉到耗时标签；流式 UI 发布按帧合并，状态事件依然有序处理；折叠内容按需挂载。注意当前 children 回调每次新建，只包一层 memo 不足以解决。

此外 `connection/environments.ts:94` 观察所有环境的 sessions 并发布新环境快照，后台环境 token 也可能扩大更新范围；应发布稳定的环境摘要。Sidebar 全量排序、Composer 全量订阅也应改为所需字段订阅。并非每次都会重建 Tiptap editor，已有稳定 editor 实例应保留。

### 3. 文件树在同目录切会话时丢缓存，挂载还会重复读根目录

证据：`shell/FilesPanel.tsx:49` key 含 thread.id；`:67` 的目录、展开和查询均为组件本地状态。`:147` 目录 effect 发起首轮读取，`:253` fileRevision effect 初次执行就推进 generation 和 revision，导致首轮结果失效并再次读取。`conversation/Details.tsx:53` 的 Tabs.Content 未 forceMount，切换文件/Git 页签也是卸载来源。

建议目录数据按环境身份 + cwd + 相对目录缓存，与组件挂载分离。同 cwd 切会话保留展开、选中、搜索和滚动；不同 cwd 分开保存。首次 revision effect 不应制造失效；已有行刷新期间保留的逻辑继续保留。

### 4. 文件后台轮询随打开数量增长，慢请求能够重叠

证据：`files/store.ts:146` 每个打开文档有 watch 加 5 秒 setInterval。N 个普通文件理论约 12N 次 fs/readFile/分钟，另加 watch 触发；这是代码推导，不是网络实测。面板隐藏不停止 store 轮询。`:310` read 用 loading 防重，但后台读取 `:317` 写 loading:false，无法挡住下一次后台请求。即使内容没变也解码全文并发布新状态。

建议每文件 single-flight，读取期间的失效合并为最多一轮补读；未变化不发布。可见文件优先、非活跃文档降频、页面隐藏暂停或大幅降频，恢复焦点校验。保留未保存文本及外部变更冲突检测，不能用省请求牺牲编辑安全。

### 5. Git 共享缓存已有，但失效机制放大请求

证据：`shell/workspace-git.ts:159` 按 connection、epoch、scope、cwd 共享。`:184` 每个 hook 调用者监听同一 files.revision，各自 refresh；多个消费者可令 busy/pending 在一次保存后追加第二轮。每轮 `:58` status 后 `:65` rev-parse 共两条命令。`:108` 任意会话的 diff/completed 都刷新，缺少 cwd 过滤。

建议将失效订阅收口到 store，按 revision 去重、按工作区过滤、短窗口合并事件；repoRoot 单独缓存。同一工作区无需因不同消费者各跑一轮。现有 busy/pending 避免并行，但不是限频器。

## 哪些请求是必要的

`sessions/store.ts:101` discovery 在前台每 5/10 秒发现其他客户端会话；只读活动会话 history sync 每 2 秒，空闲每 10 秒。后台环境降至 30 秒，页面隐藏降至 60 秒。Polling 已保证单个任务不重叠，editable 会话不走只读历史轮询。不能直接删除，否则其他客户端写入和完成状态会失联。

可优化为重返近期未失效会话时复用短期校验结果、活动尾部增量同步；只有确认通知覆盖能力后，才减少对应兜底。子代理 observer 同样有增量和单飞，轮询用于缺失通知，不是无条件无效请求。

搜索已有 250ms 防抖、分页和过期结果拦截；版本检查已有 TTL 和在途合并。HTTP 静态资产有哈希长期缓存，UI/Monaco/Mermaid 有懒加载。生产 HTTP 未压缩可影响远程首次下载，但不是当前切会话重复读取的主要原因。WebSocket bridge 有缓冲上限；未发现足够证据将额外 Git/文件负载归因于本仓库服务端计算。

## 缓存设计建议

| 数据               | 缓存身份                            | 展示与刷新策略                                                        |
| ------------------ | ----------------------------------- | --------------------------------------------------------------------- |
| 会话内容           | 环境/账号作用域 + threadId          | 内存优先；命中立即显示，按失效/同步时间后台校验；保存完整度和分页游标 |
| 阅读位置、展开状态 | 同上                                | 保存消息 ID + 相对偏移及是否跟随底部，恢复锚点而非仅恢复 scrollTop    |
| 文件目录           | 环境作用域 + 规范化 cwd + directory | 同目录共享，watch 精确失效，焦点和低频兜底；展开状态与数据分离        |
| Git 状态           | 环境作用域 + 仓库/worktree 身份     | 共享最近成功结果，事件合并、后台刷新；旧值显示时间/过期提示           |
| 文件内容           | 环境作用域 + 规范化 path            | 活跃/dirty 保留，干净非活跃文件可 LRU；保存前仍执行必要的冲突校验     |
| 搜索结果           | 环境作用域 + 查询条件 + cursor      | 小容量短 TTL，防抖和单飞；不混入正文缓存                              |

先做有界内存缓存，无需先持久化全部正文。LRU 同时看字节、会话数和最近访问；不要只限制“缓存 20 个会话”，因为单个会话可能很大。持久化是否值得应在内存缓存和页面恢复需求明确后决定，草稿是单独的保留策略。

环境身份隔离与连接 epoch 不同：前者决定数据能否共享，后者用来拒绝旧连接响应。重连可保留可展示快照，但必须标记 stale；切到不同环境/账号绝不能沿用旧缓存。

## 时序约束

1. A→B→A 时，响应只更新自己的缓存项；selectedId 只由导航意图决定。旧请求不能清掉新请求的 loading/error。
2. 每个资源维护 request generation，保存/删除/回滚另有 mutation revision。迟到读取不得覆盖后续变更。单飞只省请求，不能替代版本检查。
3. 历史快照与流式 delta 按 turnId/itemId 合并。保持服务端顺序，保留新尾部，终态不能被旧快照改回执行中；不要按文本长度或 updatedAt 独自判断新旧。
4. 当前已有 epoch、selectionGeneration、historyRevisions、终态和前缀保护，应保留。回滚的删除语义不同于普通增量合并，需要显式截断，不能复活旧 turn。
5. 同名路径在不同工作区/环境独立；同 cwd 的不同会话共享目录数据，但待发送引用仍关联当前会话。
6. 刷新失败保留有效旧结果并标记 stale，首次加载失败才展示空态错误；写操作前执行所需最新校验。

## 实施与验收顺序

1. 修复展示资格与同步标记耦合、文件树重挂载/首轮重复读、Markdown 表格组件身份；保存阅读位置。
2. 收口 Git 失效，文件读取 single-flight、不可见降频、不变不发布。
3. 拆分 store 订阅与历史渲染边界，计时器下沉、流式按帧发布、滚动局部锚点。
4. 分页展示与有界缓存；量化后决定是否需要更复杂的虚拟化。

验收应覆盖：A→B→A；同 cwd/不同 cwd；活动/空闲/只读/新建/激活会话；慢请求乱序；刷新失败；重连和换环境；回滚中读取；10 个打开文件且面板隐藏；表格横向滚动；200 轮长会话流式输出。
